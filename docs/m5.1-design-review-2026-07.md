## 3. Compatibility

### 3.1 The uniform mechanical pattern

For each site: partition the source rows into those carrying a profile id and those without; fetch `profiles` by `.in('id', …)` for the first partition and (only when non-empty) by the existing legacy key for the second; assemble the *same map, keyed by the same value the renderer already uses* (e.g. `map[f.entity_id] = byId[f.target_profile_id] ?? …`). **Renderers are not touched.** Selected columns are unchanged plus `id`. Since M2/M3/F1, the profile-id partition is 100% of rows for follows and venue_enquiries in current data, and all-but-the-designed-NULLs for lineup_members.

Why each neutrality property holds:
- **Visual output identical:** same columns fetched, same map keys consumed by unchanged renderers; for every row where legacy and profile keys coexist, M3's zero-mismatch verification (re-affirmed by M2 dual-write and F1) guarantees both keys name the same profile row — so the same fields render.
- **Ordering identical:** every list's order comes from the relationship-row query (`order('created_at' …)` etc.), which is untouched; the profiles fetch only populates lookup maps, and map assembly order does not affect render order.
- **Permissions identical:** `profiles` public read is `true` regardless of which column filters it; the relationship-row queries (RLS-scoped) are unchanged. No RLS surface changes in any direction.
- **Only the identity lookup changes:** the diff at every site is the id-list construction, the fetch filter, and the map assembly line.

### 3.2 The one implementation discipline that matters

D5/D6: the renderers look profiles up by `follows.entity_id`. The map must therefore stay keyed by `f.entity_id` (per follow row), with the *value* found via `target_profile_id`. Keying by any profile field instead would silently break unclaimed-target rows (where `entity_id` = profile id) or multi-type targets. This is called out because it is the only place the pattern could be misapplied while appearing to work on the happy path.

### 3.3 Disclosed caveat — D1/D2 multi-type owners (approval requested)

At HEAD, D1/D2 join by `user_id` with **no type filter** and key their maps by `user_id`. For an account owning several profiles (the test account owns five), the fetch returns *all* of that account's rows and the last-processed row wins — the displayed socials/genre enrichment for that owner's slots is **database-row-order nondeterministic today**. The id-join necessarily replaces this with the booked profile's own data (deterministic, and arguably what the lineup row always meant). For single-type owners — every real-world performer today except the test account — output is byte-identical. Strictly, then, D1/D2 do not preserve "identical output" for multi-type owners; they replace an unstable pick with one of its possible outcomes. Options: (a) accept as-is (recommended — no stable behaviour exists to preserve, and the affected data is the test account's own slots), or (b) drop D1/D2 from M5.1 and carry the nondeterminism until M8 forces the change anyway. The review recommends (a) with the caveat recorded in the evidence.

## 5. Rollback

Pure `git revert` of the M5.1 commit(s); **code-only, no database dependency in either direction**. M5.1 writes nothing, reads only columns that have existed since M1 and been populated since M2/M3, and the legacy columns it stops reading remain present and dual-written until M8 — so reverting restores exactly today's behaviour. There is no data to revert and no window in which rollback degrades (until M8 drops the legacy columns, at which point *not* having M5.1 is what breaks — the reason this milestone exists).
