# M0 Audit Report — 2026-07-11

**Type:** Read-only audit baseline. No schema changes, policy changes, migrations, or code changes were made during M0. This document records observed state only.

---

## 1. Executive Summary

M0 (preflight inventory, census, and freeze) has been completed as a read-only audit. Every query executed was a `SELECT` against the live production database. The audit covers: a fresh RLS policy inventory across every migration-relevant table, a data census across `follows`, `lineup_members`, `applications`, `venue_enquiries`, `venue_availability`, `events.host_id`, and `placeholder_profiles`, and confirmation of the automated backup state.

No orphaned rows were found in `lineup_members`, `applications`, `venue_enquiries`, or `venue_availability`. One ambiguous follow was identified. A significant proportion of `events.host_id` values point to non-venue/host-typed profiles. Automated backups are current; a full restore rehearsal has not yet been performed and is recorded as an outstanding operational item, not a blocker.

This report is the audited baseline the identity migration (M1 onward) will reference. No migration decisions, fixes, or implementation are included.

## 4. Observed Findings and Anomalies

### 4.1 Observed Policy State

- `profiles` contains two functionally overlapping public SELECT policies.
- `events` contains two functionally overlapping public SELECT policies.
- `artist_availability` exposes a public read policy, while `venue_availability`, `band_availability`, and `standup_availability` do not.
- `placeholder_profiles`, `follows`, `lineup_members`, and `venue_enquiries` match the expected migration baseline.

### 4.2 Data Findings

- **One ambiguous follow exists**: a follow on "The Bellingen Brewing Co" where the target user owns both a `punter` and a `venue` profile. The follow's own `entity_type` column already records `venue`, distinguishing this from the general ambiguous-follow risk category.
- **Zero orphaned rows** across `lineup_members`, `applications`, `venue_enquiries`, and `venue_availability`.
- **`events.host_id` type mismatch**: 72 of 120 events (60%) have a `host_id` whose profile type is not `venue` or `host` — the majority of events in this dataset are not hosted by venue/host-typed profiles.
- **Zero cross-keyspace collisions** between `placeholder_profiles` and `profiles` ids.
- **One user owns four profile types** (non-punter); thirteen users own exactly one.
- `placeholder_profiles` currently holds one row, unclaimed, not a duplicate.

## 5. Migration Implications

- The single identified ambiguous follow, and the general ambiguous-follows category it represents, is directly relevant to the M3 backfill phase's follows resolution work already described in the frozen migration plan.
- The zero-orphan result across all four checked relationship tables means the M3 backfill has no known orphaned-row cases to resolve in this dataset as it currently stands.
- The `events.host_id` type-mismatch finding (72 of 120 events) is directly relevant to the events attribution split described in the frozen migration plan (`events.host_id` for authorization vs. `venue_profile_id` for public attribution).
- The zero-collision result between `placeholder_profiles` and `profiles` ids means the M3 placeholder-promotion step (preserving UUIDs) has no known id conflicts to contend with in this dataset as it currently stands.
- The multi-type profile ownership distribution (13 users at 1 type, 1 user at 4 types) reflects the real-world shape of the "one user, multiple typed profiles" pattern the migration plan's risk register already anticipated.
